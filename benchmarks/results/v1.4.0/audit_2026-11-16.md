# Dispatch and history audit measurements — 16 November 2026

These are local screening measurements of unreleased changes, not a claim about the published 1.4.0 wheel. The production cache and matched-buffer policies were retained. The diagnostic collector scripts are included as text in the manifest for reproducibility.

## Reproduction and limits

The shared pyperf runner executes `python -m benchmarks.benchmark_dispatch_pressure --suite routing` or `--suite matching`. Each case uses three fresh workers, three values, one warmup and a 30 ms minimum value. Routing was measured baseline/FIFO and then FIFO/baseline; matching was measured once per candidate. Source copies originated from `7a30a9e`; raw files record full source SHA-256, interpreter, compiler and host. Git revision is `unknown` inside the isolated copies; the manifest retains the exact candidate patches. The later history-only change does not alter dispatch.

Routing covers 16/64/65/80/256/1000 keys, 0/100/1024 wildcard subscribers, uniform access and a late hot key after filling the first 64 cache entries. Matching covers 64/100/2048 subscribers and 0/1/10/50/100 percent acceptance (rounded down to whole subscribers). This is not a Zipf, subscription-churn, multi-publisher or free-threaded matrix.

Raw pyperf files contain 174 benchmark results; the comparison CSV contains 87 pairs. Ratios above one favor the candidate. CV columns must be considered alongside the ratios. The host uses a powersave governor and some cases have substantial dispersion; no significance or universal speedup is claimed.

## Routing decision

FIFO improves admission of late hot keys without changing the 64-entry bound. It also changes the cache behavior for uniform high-cardinality traffic. The candidate is promising, but this screen is insufficient to adopt it across platforms and contention profiles.

## Matched-buffer decision

The isolated candidate enlarges the fixed stack buffer from 64 to 2048 pointers, eliminating heap allocations for the screened sizes without introducing allocation after filtering side effects. It costs 16 KiB instead of 512 bytes on a 64-bit host. This is a sensitivity screen, not a direct malloc profiler: stack layout also changes. It did not show a consistent benefit and several cases regressed or were noisy. Retain the existing buffer. Dynamic growth during matching was not implemented because its allocation-failure semantics require a separate design.

## History correctness tradeoff

All matching now runs outside the storage lock. Exact built-in cache keys retain cache hits; misses use immutable snapshots and only publish cached results if the snapshot remains current. `_query_by_type` now has real callers for both limited and unlimited results, so its limited branch is no longer unreachable. Tuple subclasses use the general path. The deque replacement guard remains.

The history JSON compares the `94b5cbb` implementation and the current implementation in one process, with five reconstructed histories per scenario at 1k/10k/100k events and first/last/no matches. Cold calls and subsequent warm calls are separate. This is an order-sensitive diagnostic, not a multi-process pyperf A/B result. A first snapshot-only version measured about 767 us for a cold latest call at 100k entries versus about 3 us before. The final version returns exact-type tail matches using type identity without running user code under the lock. Other cold filtered latest calls may still pay O(n) snapshot cost. Unfiltered latest keeps its O(1) path. The correctness tests prove writers can progress during user-defined matching; this timing screen does not quantify writer P99.

## Native ownership review

The matched array owns its allocation, while its subscriber pointers borrow references from the owned snapshot. The snapshot remains alive across selection and callback delivery; success clears it after freeing a heap matched array, and failure cleanup releases both. Error-list ownership is released on subsequent result/hook failures. No publish-wide ownership rewrite was justified by this review. Allocator regression tests now cover finite claim/restore and metrics snapshots; leak detection, C branch coverage and exhaustive publish allocation injection remain separate validation work.
