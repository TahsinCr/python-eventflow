# EventFlow 1.3.2 and 1.4.0 benchmark comparison

## Summary

The earlier report contained only native-focused 1.4.0 measurements and missed
the release's broader pure-Python work. A fresh Python-only screen now covers
the same 13 benchmark modules as the archived 1.3.2 screen, with 180 matched
cases and three new 1.4.0 routing-key cases. The native history and routing
experiments remain a separate, narrower data set.

The two Python screens have matching benchmark names and stable workload
parameters for all 180 shared cases, and use the same pyperf version and
broad-screen settings. Run-specific source, interpreter, kernel and machine
state metadata differs and is recorded with the raw results.
`pyperf compare_to` reports at least 5% faster results for 107 cases and at
least 5% slower results for 9; the other cases do not meet both the report's
5% threshold and pyperf's comparison criteria. These are useful broad
measurements of the pure-Python changes, with the interpreter, kernel, date,
and source-snapshot limitations recorded below. They are not a hardware- or
platform-independent release guarantee.

| Large-history repeats | CPython 3.10.22 and 3.14.9 | 12 cases per build at 100,000 events |

The measurements identify EventFlow 1.3.2, source revision
`4af998df85e8fa779e4fec709a01765ed5018ca3`, and source fingerprint
`5276989cf35716861fd9104c3a795ff961acdceca1c45172b1fcf0052d38bdae`. The
recorded source tree was clean. The host was an Intel Core i7-12700H running
Arch Linux x86_64; pyperf was 2.11.0. The benchmark report recorded CPU
affinity and GIL state for each run.

The broad CPython 3.14.9 screen used three processes, three measured values per
process, one warmup, and a 50 ms minimum sample. The 100,000-event repeat set
used five processes and ten values per case. Across the 409 summary rows, 179
had a coefficient of variation (CV) of at least 1%, and 39 had a CV of at
least 5%. The distribution files therefore matter: small differences should
not be ranked from the CSV means alone.

The 1.3.2 source revision is recorded in every result, but its commit object is
not available in the current Git object graph. Its source fingerprint and
measurement metadata remain in the archived results.

## Pure-Python release comparison

The comparison pairs all 180 common case names from the 1.3.2 and 1.4.0 broad
screens. Their stable workload parameters match case by case. Run-specific
`cpu_temp` metadata differs in 27 pairs and `runnable_threads` differs in 72;
these fields describe host state rather than the configured workload. The
1.4.0 screen also adds three `sync/routing-key/` cases for 10, 100 and 1,000
subscriptions; they have no 1.3.2 counterpart and are excluded from release
comparison counts. Both runs use pyperf 2.11.0, three processes, three values
per process, one warmup, a 50 ms minimum sample and affinity CPU 4. CPython
changed from 3.14.9 to 3.14.10 and the Linux kernel from 7.2.14 to 7.2.15.
This is a close, same-host comparison, not a perfectly controlled
same-interpreter experiment.

Counts below include only the cases shown by `pyperf compare_to` with a 5%
minimum-speed threshold. Cases omitted from this table were either below that
threshold or did not meet pyperf's comparison criteria.

| --- | ---: | ---: | ---: |
| Bridge publisher scaling | 10 | 9 | 0 |
| Bridges and queue handoff | 4 | 2 | 0 |
| Coalescing | 16 | 14 | 0 |
| Components: cache, state, policy, metrics, context | 13 | 10 | 0 |
| Keyed limiter | 3 | 0 | 0 |
| Lifecycle and callbacks | 9 | 4 | 1 |

The three new 1.4.0 routing-key cases measured 2.27 µs at 10 subscriptions,
2.27 µs at 100, and 2.31 µs at 1,000. They document the indexed-routing
workload but are not compared with an older implementation.

`query-all` reuses the cached history snapshot, and a newest-match query with

cache, policy, coalescer, resilience and runtime rows also show substantial
improvements without a compiled backend.

## History query: the valid 1.4.0 backend comparison

The workload queried a 100,000-event history using an unlimited exact
single-type `EventFilter`; every second event matched. The same production
query was measured with the normal Python path and the opt-in Cython history
kernel. Each of the four pyperf runs retained 120 measured values. The run
order was reversed to reduce order bias.

| Run order | Python backend | Cython backend | CV, Python / Cython |
| --- | ---: | ---: | ---: |
| Python first, Cython second | 5.71 ms | 3.06 ms | 3.9% / 3.7% |
| Cython first, Python second | 6.12 ms | 3.10 ms | 5.8% / 4.1% |

Across the two orders, the arithmetic mean of the reported run means is 5.92
ms for Python and 3.08 ms for Cython. That is about 1.92× throughput-equivalent
latency improvement, or 47.9% lower time for this exact query. The run-to-run
direction is consistent, but all CV values exceed pyperf's strict 1% stability
target. Treat this as one-host evidence for the unlimited, single-type,
100,000-event history path. It does not establish an application-wide gain or
cover limited queries, predicates, other history sizes, or other platforms.

## Routing: 1.4.0 results remain inconclusive

The production routing comparison used 2,048 subscriptions, seven keys, 20%
wildcards, and 653 selected callbacks. The protocol started with five
independent processes at 2,000 publishes per publisher. Since the cross-process
P99 CV exceeded the 10% stopping threshold, it escalated every candidate to
five processes at 5,000 publishes per publisher. The final P99 CV still
exceeded the threshold for both backends.

| Publishers | Backend | Median P50 | Median P99 | Throughput | Cross-process P99 CV |
| ---: | --- | ---: | ---: | ---: | ---: |
| 1 | Python | 490 µs | 1,057 µs | 1,859 publishes/s | 21.1% |
| 1 | C | 457 µs | 977 µs | 2,045 publishes/s | 26.0% |
| 4 | Python | 2,519 µs | 12,831 µs | 1,270 publishes/s | 19.4% |
| 4 | C | 2,181 µs | 23,672 µs | 1,472 publishes/s | 30.6% |

At four publishers, C had 13.4% lower median P50 and 15.9% higher measured
throughput, but its median P99 was 84.5% higher. The final P99 CV remained
above the predeclared 10% threshold for every row. The routing comparison is
inconclusive and does not support enabling C by default.

The original per-publish raw samples were not retained in the repository; the
two CSV files are the compact summaries. They contain the per-process values
and provenance needed to audit the reported medians and variation:

## Release-level interpretation

The comparison now includes the non-native performance work in 1.4.0. The
strongest and most consistent areas are history snapshots and bounded queries,
sync/async pipelines, subscriber dispatch, callback invocation, policy/cache
operations, coalescing, resilience, and sync runtime contention. The stream
and keyed-limiter cases did not show a pyperf-significant change of at least
5% in this screen. Nine cases were flagged slower; replay cancellation/query
windows need focused repeats, particularly where current CV reached 26% or
32%.

The version comparison is still historical rather than perfectly controlled:
CPython changed from 3.14.9 to 3.14.10, the Linux kernel changed from 7.2.14 to
7.2.15, and the exact 1.3.2 benchmark source commit is no longer present in
the Git object graph. All 180 case names and stable workload parameters match,
and both sets used the same host model, affinity, pyperf release and broad-
screen settings. Some run-specific machine-state metadata also differs, as
noted above; the source fingerprints remain distinct and are preserved in every
raw result. Treat the Python comparison as strong same-host evidence, not as a
release gate or a guarantee for every supported platform.

The native results answer a separate question. Cython shows a clear
within-1.4.0 benefit for one large type-only history query, while C routing
remains inconclusive under publisher contention. These experiments do not
replace or summarize the broad pure-Python comparison above.
